# Auto-generated rule: a line-regex frontmatter validator is blind to unparseable YAML and mis-measures block scalars

check-agents.mjs validates frontmatter with line-oriented regexes instead of a parser. That is structurally blind to the defect class it exists to catch: an unquoted single-line description containing a ': ' is not YAML, but '^description:' matches it perfectly. 12 of 46 SKILL.md files sat unparseable in the tree because no skills-side check existed and the agents-side prior art could not have found it anyway. The same regex class has a second, quieter failure: a block-scalar extractor whose terminating lookahead offers a bare end-of-line alternative under the /m flag captures only the FIRST folded line, reporting 97 chars for a 329-char description and making every length assertion built on it vacuous. Fix both by parsing (js-yaml CORE_SCHEMA, as check-commands.mjs already does), never by tightening the regex. Note also the sign flip across surfaces: check-agents.mjs BANS 'description: >' because the agent loader cannot read it, while for SKILL.md that same form is the only one that makes the ': ' collision structurally impossible — porting the rule across surfaces would have forbidden the fix.

## Evidence
2026-08-15: two independent parsers (js-yaml CORE_SCHEMA + yaml 2.x) agreed on 46 SKILL.md files: 34 parse, 12 broken, all 12 on the description line. After repair: 46/46 parse. Fake-regression observed — restoring HEAD:skills/debug/SKILL.md into a mktemp copy turned the new check-skills.mjs red (exit 1, 'bad indentation of a mapping entry at frontmatter line 2, column 175'), repairing it returned exit 0. The block-scalar extractor bug was proven pre-existing on files never touched: session-start helper=97 vs yaml-truth=329, autopilot 107 vs 555, bootstrap 98 vs 341.

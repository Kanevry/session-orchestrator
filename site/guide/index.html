Guide

Install once, set up once, then run your first session.

From your task to checked work. Pick your coding tool and follow its five steps.

Node.js 24 or later · MIT · guidance reviewed against source on 2026-10-23

New to these words? A short glossary
Repository
The folder with your project's files and their full history.
Commit
A saved step in that history, with a short note on what changed.
Branch
A separate line of work, so a change can be tried without touching the main version.
Issue
A to-do note on GitLab or GitHub: a bug, a wish or an open question.
CI or pipeline
Checks that run on a server after each change and report whether the tests still pass.
Hook
A small check your coding tool runs at fixed moments, for example before a command, and which can stop it.

Claude Code

Everything works here: agents run in parallel, and the guards block.

  1. You need Terminal

    Node.js 24 or later (check with node --version), a Git repository and Claude Code.

  2. Install Chat in your coding tool

    /plugin marketplace add Kanevry/session-orchestrator

    /plugin install session-orchestrator@kanevry

    Current Claude Code installs the Node dependencies itself. Only if a command fails, use the dependency check.

  3. Set up once Chat in your coding tool

    /bootstrap --fast --no-interview

    No questions, sensible defaults. If you want to choose the settings yourself, run /bootstrap and answer the interview.

  4. Your first session Chat in your coding tool

    /session feature add a CSV export

    Then /go, then /close.

    What the three commands do
    /sessionreads your repository and proposes what to work on; nothing changes until you agree
    /godoes the agreed work in rounds (waves) and checks each round with your tests
    /closeruns the full check, commits, and writes down what is left as issues

  5. What success looks like

    You see a short report and a proposed plan. Nothing in your code has changed yet. You answer with /go or correct the plan.

    After /close you see what was done, what was checked and which issues were opened for the rest.

Last documented install run: 2026-10-28, plugin 5.14.0, Claude Code 2.1.312 on macOS (Node 24.22.1), from the public GitHub mirror in an empty profile. marketplace add and install exit 0, 11 of 11 runtime dependencies resolve, and bootstrap --fast --no-interview wrote the Session Config block. A feature session (model gpt-6-sol on an Anthropic-compatible endpoint) ended at a plan offering /go after one or two answered questions (scope, CI), with no project file changed. In 2 of 5 runs a model-chosen command printed the session's own messaging token, which the plugin's secret detector flagged (#1873). Re-run 2026-10-29 on plugin 5.16.0: install and readiness passed (11 of 11), bootstrap and session not measurable because the model endpoint answered 429.

Codex CLI

Everything works here, with one difference: the file list is an instruction. Codex edits files through apply_patch, which the file-scope guard does not read. The destructive-command guard blocks.

  1. You need Terminal

    Node.js 24 or later, a Git repository and Codex CLI 0.160 or later (check with codex --version).

  2. Install Terminal

    git clone https://github.com/Kanevry/session-orchestrator.git ~/Projects/session-orchestrator

    cd ~/Projects/session-orchestrator && npm install && node scripts/codex-install.mjs

    Keep the clone in ~/Projects/session-orchestrator. To update later, run git pull && npm install && node scripts/codex-install.mjs there, then start a fresh task.

    What the installer changes:

    • For your user, in every project: a packed copy of the plugin in ~/.cache/session-orchestrator/plugin-package/, added to Codex as session-orchestrator@kanevry. Codex copies it into its plugin cache under ~/.codex/plugins/cache/.
    • Removed: an older session-orchestrator@local or session-orchestrator@openai-curated install, if you have one.
    • Not touched: your projects, and the approval of the hooks.

  3. Approve the hooks Chat in your coding tool

    Start a fresh Codex task, or restart Codex. Type /hooks, read the Session Orchestrator hooks and approve them. The installer never does this for you.

    Until you approve them, the hooks do not run, so no Session Orchestrator guard blocks a destructive command. If the hooks seem silent later, open /hooks again and check that they are approved.

  4. Set up once per project Chat in your coding tool

    $session-orchestrator:bootstrap --fast --no-interview

    Run it in the Codex chat inside your project. It writes .orchestrator/ and a ## Session Config block in AGENTS.md. It may still ask for the setup tier and the project type; then answer those two questions. To choose every setting yourself, run $session-orchestrator:bootstrap and answer the interview.

  5. Your first session Chat in your coding tool

    $session-orchestrator:session feature add a CSV export

    Then $session-orchestrator:go, then $session-orchestrator:close. These are skill picks in the Codex chat. Plain /go and /close do not work in Codex.

  6. What success looks like

    You see a short report and a proposed plan. Nothing in your code has changed yet. You answer with $session-orchestrator:go or correct the plan.

    After $session-orchestrator:close you see what was done, what was checked and which issues were opened for the rest.

Last documented install run: 2026-10-28, plugin 5.14.0, Codex CLI 0.160.1 on macOS (Node 24.22.1), from the public GitHub mirror in an empty profile. The clone installer exits 0 with 11 of 11 runtime dependencies; the short marketplace form exits 0 but its new cache had 0 of 11 (measured six times) until the repair step brought it to 11 of 11. With model gpt-5.6-sol 3 of 4 runs (both paths) ended a feature session at a plan after two or three answered questions, with no project file changed; in 2 of the 4 runs bootstrap --fast --no-interview asked for the tier and archetype instead of completing. With gpt-6-sol the session wrote the file without a plan (3 of 3 runs), a model behaviour. Re-run 2026-10-29 on plugin 5.16.0: both installs and the repair (0 → 11 of 11) passed, both model sessions with gpt-6-sol failed, and after the first codex exec the short-form cache had lost its dependencies again (#1878).

When you need more

Open only what you need.

Before you start: requirements and the instruction file

Windows is barely tested. macOS and Linux run the full tests in CI; Windows only a smoke test. The shell hooks and the optional MCP server need WSL or Git Bash. Some optional workflows (the plugin validator, some wave-scope snippets, the MCP server) also need jq.

Your settings live in the project’s instruction file: CLAUDE.md on Claude Code and Cursor, AGENTS.md on Codex CLI and Pi. The contents are the same.

Each tool keeps its own session state (STATE.md in .claude/, .codex/, .cursor/ or .pi/). Session records and lessons in .orchestrator/metrics/ are shared, and so are the issues. Switching tools keeps your history.

Configuration: the Session Config

Bootstrap writes this block for you. These seven fields are the minimum:

## Session Config

test-command: npm test
typecheck-command: npm run typecheck
lint-command: npm run lint
agents-per-wave: 6
waves: 5
persistence: true
enforcement: warn

The heading must read ## Session Config exactly. Pasting the block alone does not finish setup: bootstrap also writes .orchestrator/bootstrap.lock, so run bootstrap once.

enforcement takes strict (edits outside the file list are blocked), warn (they are reported) or off. Every key: configuration reference.

What the guards block, and where they stop

The destructive-command guard follows .orchestrator/policy/blocked-commands.json: 14 blocking and 4 warning rules. It blocks hard resets, discarding checkouts, forced cleaning, destructive removal, force-push, SQL DROP TABLE and deleting the session records. It warns on soft resets, stash and git push --force-with-lease.

Guard behaviour per coding tool
ToolDangerous commandsEdits outside the file list
Claude Codeblocked by a hookblocked in strict
Codex CLIblocked by a hook (Codex honours the deny)an instruction only
Cursor IDEthrough a bridgeblocked in strict
Pithrough a bridgeblocked in strict

A file list is not filesystem isolation. Several sessions can share one working copy, which is why a stash or a reset is guarded: it can take a neighbour’s work.

What to do when a command is blocked

Read the reason in the message first. Most blocks protect work you did not create.

If you really mean it, run the command yourself in your own terminal, or relax the guard from outside the agent’s reach: start the session with SO_HOOK_PROFILE=relaxed (or set hooks.profile: relaxed in your host-local owner.yaml), which only warns on cases the guard can prove recoverable. SO_DISABLED_HOOKS=pre-bash-destructive-guard turns the guard off. The old allow-destructive-ops: true line in the Session Config is ignored, because the agent could write it itself.

If a legitimate edit is blocked by the file list, check the plan and the other agents’ files before you add the path. enforcement: off turns off the file-scope and blocked-command checks, not the destructive-command guard.

When something goes wrong

A command fails right after installing on Claude Code. Check the dependencies once. In a terminal, run claude plugin list --json, take the installPath of the enabled session-orchestrator@kanevry entry, then:

cd "/absolute/installPath/from/the/list" && { [ -d node_modules/js-yaml ] && echo "dependencies present" || npm install; }

If it installed anything, restart Claude Code.

Hooks cannot find Node. Hooks run in your coding tool’s environment, not your login shell. Set SO_NODE_BIN to the absolute path of your Node binary, or start the tool from a shell where node works.

Cursor files landed in the wrong project. Rerun the installer with the absolute project path.

The summary does not match what you saw. Compare it with the latest session record:

tail -1 .orchestrator/metrics/sessions.jsonl | jq '{session_id, total_waves, total_agents, total_files_changed}'

Look closer at total_agents: 0 after agents plainly worked, undefined anywhere, or -abandoned- in the id after a clean /close. Then check what actually changed on disk before you build on it. Still stuck: open an issue.

How it works

Five steps.
You type three commands.

One task from start to finish: “Add a CSV export to the dashboard.” The task is an example; the commands and the steps are the real ones.

Once per repository, before the first session Type /bootstrap. It sets up your repository; add --fast --no-interview to skip its questions. After that, each task needs only the three commands below. On Codex you pick every command as a skill: $session-orchestrator:bootstrap, $session-orchestrator:session, $session-orchestrator:go, $session-orchestrator:close.

  1. 1Read

    You type/session feature add a CSV export

    It reads your code, open issues, recent commits and the last session, then recommends what to work on. Nothing has changed yet.

    You pick an option or answer in your own words. Then it shows the plan. Nothing is built before you type /go.

  2. 2Plan

    You type/go

    Correct the plan by writing in the chat, or say yes by typing /go. Every agent gets its own list of files, and overlaps are rejected before work starts.

  3. 3Go

    You donothing. Watch, or do something else.

    The agents work in rounds: side by side on Claude Code and Codex, one after another on Cursor and Pi.

  4. 4Check

    You donothing.

    After each round your tests and typecheck run. A failing test becomes a fix task for the next round, so the error is caught in the round that made it.

  5. 5Close

    You type/close

    It runs the full check, compares the result with the plan, commits the work and turns what is left into issues. The next /session starts here.

Nothing gets lost.

A crash, a closed laptop or a long weekend does not cost you the work. STATE.md records every finished round, so the next /session offers to resume. What /close could not finish is waiting as an issue on GitLab or GitHub.

The session film

How it fits together

Your tool writes the code.
This plugin keeps the work in order.

It is not another AI. It adds a fixed way of working to the coding tool you already use, and everything it keeps is plain text in your repository.

  • In your repository: plain text you can read and delete. STATE.md for the running session, rules under .claude/rules/.
  • On GitLab or GitHub: one issue for each thing that is left, so it cannot be forgotten.
  • Nowhere else: no account and no server of its own. By default, besides your coding tool and your Git host, the plugin only asks npm for updates, and you can switch that off. Features you turn on yourself, such as usage data or remote hosts, make their own connections. Optional usage data stays off until you agree.

My recommendation

Want every guard to block, and the lead Inbox? Use Claude Code. Prefer Codex? You get the same commands as skills, agents side by side and the command guard. Only the file list per agent is an instruction, not a block, because Codex edits files through apply_patch. Cursor or Pi? Everything works, one agent after another.

A few practical questions

Questions people ask

Setup steps for each tool are at the top of this page.

Is this itself an AI that writes code?

No. It adds a workflow for planning, working and checking results. Your coding tool writes the code. Technical enforcement depends on the tool and guard configuration.

Which tools does it work with?

Claude Code runs the guard hooks directly. Cursor and Pi use bridges with documented limits. Codex CLI offers selectable workflow skills and runs the destructive-command guard as a Bash hook that blocks; its file-scope rules are instructions only, because Codex edits files through apply_patch, which the scope guard does not read. Parallel agents are available on Claude Code and Codex; Cursor and Pi run tasks sequentially.

Can a team use it?

Yes. Each person installs the plugin in their own coding tool. The Session Config in CLAUDE.md and the session records under .orchestrator/ live in the repository and are committed, so the next person's session reads what the last one left. Commits land on the branch you are on; /close pushes that branch. It creates a new branch only when you accept a worktree offer or run /autopilot.

What happens to my existing CLAUDE.md?

/bootstrap never overwrites it. It only adds the sections it needs (## Session Config, ## Dispatcher Autonomy and a short rules section) when they are missing.

Does it work with Jira or Linear?

No. Issues are read and written on GitHub or GitLab only.

What is different from just using Claude Code?

It adds a repeatable session workflow: read the project, agree the scope, divide the work into steps with declared files, and check the results between steps. The session record carries progress and unfinished work into the next session.

Does it send data anywhere?

The plugin runs locally without its own account. Optional usage telemetry is off until you consent. By default, session-start checks the npm registry for updates. Successful results are cached for 24 hours per repository; a failed request or cache write may cause another request at the next session. SO_DISABLE_UPDATE_CHECK=1 or DO_NOT_TRACK=1 disables the check. Your coding tool and configured services still use their own network connections. This website uses cookieless Vercel Web Analytics, described in its privacy policy.

Does it work on Windows?

Windows is barely tested. macOS and Linux run the full tests in CI; Windows only a smoke test. The Node core uses portable paths, but the shell-based hooks and optional MCP server need WSL or Git Bash. Treat Windows support as best-effort.

What does it cost?

Nothing for the plugin. It is free and open source under the MIT licence. You still pay for your coding tool, and a session with several agents and rounds uses more of its quota or tokens than a single chat.

Can it break my project?

It can still make mistakes. On Claude Code and Codex, an active destructive-command hook applies 14 blocking rules and 4 warning rules. Cursor and Pi use bridges with documented limits. Codex does not enforce the file-scope guard. For supported edits with an active scope hook, strict blocks violations, warn reports them, and off disables the check. Review changes and keep backups; the checks do not guarantee correct code.

Who maintains it?

Me, Bernhard Götzendorfer. I answer questions on GitHub myself. It is shipped as-is, with best-effort maintenance and no service level agreement.

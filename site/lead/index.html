Many sessions.
One lead.
One Inbox for you.

When several coding sessions run at once, one lead session watches them for you. It collects every question that needs you in one Inbox. You answer once, the sessions keep working.

Optional add-on. session-orchestrator works without it. Do you run three or more sessions side by side? Then add the lead.

Using Codex?

Codex sessions can be led like any other: they check in and get constraints. The Inbox pane is a Claude Code mod, so it runs in Claude Code and lists the Claude Code sessions.

Run the lead and its Inbox in Claude Code; your working sessions can be Claude Code or Codex.

How it works

You, one lead,
and the sessions.

The lead measures and sets the order. It starts headless runs itself, after its checks, and never opens an interactive session on its own. Inside each session, session-orchestrator does the work. A session never waits for the lead.

  • Lead

    Only one lead can act at a time: it holds a lease, like a key that only one person can have.

  • Rules

    Each repository gets an authority file, signed and committed in a folder of yours. It says what the lead may do freely, what needs your yes each time, and what never happens.

  • Gates

    Before a run and before a merge the lead measures; if it cannot measure something, it stops instead of guessing.

  • Ledger

    Decisions and merges go into a log that can only grow. ledger verify names the first line that was changed.

Limits

What works,
what does not.

Version 0.x. Commands and file formats may still change.

Works

GitLab, macOS, one host. Also without session-orchestrator, but then it sees less clearly when a session is busy.

Does not work

GitHub gates, not yet. Ledgers across hosts, planned. It never opens an interactive session on its own, by design. Pushes and merges without asking: only after you add a trusted signer. Until then each one asks you.

Get started

Install
from npm.

Needs Node.js 24 or newer, git, and glab signed in to GitLab. Current version and changelog: npm.

1. The command line tool. The command is called navigator.

npm i -g lead-session-orchestrator

navigator situation                         # the current picture on one screen
navigator status                            # all Claude sessions on this host, open questions first
navigator stop set --reason "maintenance"   # nothing new starts until you clear it

2. The Inbox. The Inbox pane is a Claude Code mod in the same npm package and needs Claude Code 2.1.296 or newer. Mods are early access in Claude Code and are not sandboxed; a Claude Code release can change them. Add it once from a shell:

claude plugin marketplace add "$(npm root -g)/lead-session-orchestrator"
claude plugin install owner-inbox@navigator-mods

Then start a new Claude Code session and type /inbox. The other mods and their options are on npm.

3. The lead. The lead is a Claude Code skill in the same package. Copy it once:

mkdir -p ~/.claude/skills
cp -R "$(npm root -g)/lead-session-orchestrator/skills/lead" ~/.claude/skills/lead

Start a new Claude Code session and type /lead. That session takes the lease, so it is the only lead on this computer. The skill names commands, not your setup: before the first run, write down which repositories it leads and your load limits for headless runs, as skills/README.md in the package describes. Headless runs also need the settings in docs/configuration.md.

4. Your sessions. Sessions that run session-orchestrator check in by themselves when they start. They need nothing extra: the lead creates the folder ~/.config/navigator when it takes the lease, and that is where they write. Sessions you start after that check in; one that was already running does not.

5. Rules, when you want them. Until you add a trusted signer, every push, merge and other action in the authority file asks you. To let the lead do some of them without asking, write one authority file per repository in a git repository of yours, commit it with your SSH signature, set authority.dir to that folder in ~/.config/navigator/estate.yaml, and add your key as a trusted signer. The steps are in the package, in docs/configuration.md.

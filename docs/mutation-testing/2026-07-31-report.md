## The survivor pattern (confirms + extends the prior finding)

The prior session found: *leaf functions tested thoroughly, wiring/config-precedence
not at all.* This round's 14 survivors split into **two** clean patterns:

**Pattern A — untested threshold/boundary comparisons (9 survivors).** Every
`<`/`<=`, `>`/`>=`, `>=1`/`>1` flip that only matters when the value sits
*exactly* on the limit survived, because the suites exercise thresholds strictly
above/below, never AT the boundary: `wr4 wr5 wr6 wr7` (wave-resource-gate),
`sr1 sr2 sr7` (session-registry), `re1` (reconcile cap), `ms5` (mode-selector filter).

**Pattern B — untested wiring / validation / fail-safe (5 survivors).** The
same class the prior round named, still under-covered: `sr4` (schema-v2 mode
type-check inversion), `sr6` (fail-open NaN-age), `sb2` (div-by-zero guard),
`re4` (confidence default), `sb4` (near-equivalent field echo).

The two 100%-kill modules (`consent`, `store`) and near-100% (`board-writer`)
are the counter-evidence: where a suite *does* enter the boundary and the
negative/error branch (consent's fail-closed precedence, store's quota/floor
boundaries, board-writer's status-sticky guards), mutants die. **A module with
100% kill-rate is a success — it needs no new tests.**

### Nameable but deferred (setup cost > W3 budget) → OPEN-QUESTIONS

> **Read these as TEST GAPS, not production defects.** A survivor means *no test
> catches the mutation* — the production code is correct; the mutant's behaviour
> is hypothetical and exists only while the mutant is applied. Three bullets in
> this section originally described the mutant's behaviour in the present tense
> as if it were production behaviour (`re1`, `sb2`, `re4`); that phrasing produced
> the false premise of issue #950 and nearly triggered a "fix" to correct code.
> Each is corrected below with the production code quoted.
>
> **Cited by symbol + search command, never by line number.** The first version of
> this section pinned line numbers, and two of its three citations were already
> wrong when a reviewer checked them (`re1` pointed at JSDoc prose, `re4` at the
> *other* bullet's code). That is not carelessness — it is what pinned line
> numbers do; `scripts/lib/scope-baseline.mjs` carries a comment saying exactly
> this about itself ("a pinned number goes stale, as this very comment did").
> Every citation below is therefore a symbol name plus the `grep` that finds it,
> which survives edits above it. Each was re-run against the working tree on
> 2026-07-31 and each anchor matches exactly one line.

- **re1** (reconcile `maxProposalsPerRun >= 1 → > 1`) — **test gap, not a bug.**
  Production — the `maxProposalsPerRun` resolution in
  `scripts/lib/reconcile/engine.mjs`, findable via
  `grep -n 'const maxProposalsPerRun =' scripts/lib/reconcile/engine.mjs` — reads
  `Number.isFinite(p) && p >= 1 ? Math.floor(p) : DEFAULT_MAX_PROPOSALS_PER_RUN`,
  so a brake setting of exactly 1 passes through correctly — measured
  `cap=1 proposed=1 capped=2`. It is the *mutant* (`>= 1` → `> 1`) that would
  fall through to the default of 10, and no test notices. Needs a
  `runReconcile({ dryRun, learnings, maxProposalsPerRun: 1 })` fixture;
  deferred for budget, repro documented. (Related in *class* to the panel-found
  "never-passed-through max-proposals" HIGH bug — but that was a real wiring
  defect elsewhere; this one is only an uncovered boundary.)
- **sb2** (scope-baseline `Math.max(plannedFiles, 1) → , 0`) — **test gap, not a
  bug.** Production — the `filesRatio` computation in
  `scripts/lib/scope-baseline.mjs`, findable via
  `grep -n 'const filesRatio' scripts/lib/scope-baseline.mjs` — divides by
  `Math.max(plannedFiles, 1)`, so `plannedFiles === 0` yields a finite ratio; the
  *mutant* would yield Infinity/NaN, and no test enters that case. Needs a full
  git-repo + STATE.md frontmatter fixture (the existing scope-baseline harness
  cost); deferred.
- **sr2** (sweep age-boundary), **sr7** (detectPeers age-boundary) — the same
  `<=`/`>` boundary semantics as sr1, but reached only through async fs registry
  setup. sr7 duplicates the `isRegistryEntryFresh` rule now pinned by sr1;
  sr2 (sweep threshold) is a lower-value boundary follow-up.
- **re4** (reconcile confidence-default `0 → 1`) — **test gap, not a bug.**
  Production — the `confidenceOf` helper in `scripts/lib/reconcile/engine.mjs`,
  findable via `grep -n 'const confidenceOf' scripts/lib/reconcile/engine.mjs` —
  defaults a non-numeric
  `confidence` to `0`, which under the DESC sort puts it at the *bottom* of the
  volume-brake cut, as intended; the *mutant*'s default of `1` would lift it, and
  no test distinguishes the two. Narrow, low blast-radius. Follow-up.
